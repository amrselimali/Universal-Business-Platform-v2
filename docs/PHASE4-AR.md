## 3) مقارنة دورة العمل بـ Odoo — أين نطابق وأين نختلف ولماذا

| الدورة | Odoo | نحن | الفرق والسبب |
|---|---|---|---|
| البيع | Quotation → Sales Order → Delivery → Invoice → Payment | **Booking (التزام) → Delivery/Execution → Invoice → Payment** | لا يوجد عرض سعر/أمر بيع. الحجز هو الالتزام (D2)، ولا بيع مباشر: كل فاتورة مرتبطة ببند حجز (D3) — **أشدّ من Odoo** |
| الشراء | RFQ → PO → Receipt → Bill → Payment (3-way match) | **Purchase Invoice → Receipt داخلي** | أوامر الشراء خارج النطاق؛ لا مطابقة ثلاثية؛ لذلك `purchase_variance` يظهر في المرتجعات وفروق المتوسط فقط (D22) |
| المخزون | Quants + Lots/Serial + Expiration + FEFO + `free_qty` | **stock_balances + stock_lots + FEFO + reserved_qty** | مطابق وظيفياً؛ FEFO و`free_qty` يُنفَّذان في 4A-2 (D16) |
| التكلفة | Perpetual, AVCO/FIFO | **المتوسط المرجح المتحرك (AVCO) فقط** | تنفيذ حالي مُختبر في `fn_stock_apply`؛ FIFO غير مطلوب |
| نقاط البيع | POS Session + Payment Methods + Cash Control | **cashier_shifts + treasury_methods + فرق عهدة** | مطابق؛ POS يُنشئ حجزاً فورياً (D3) |
| المواعيد | Appointments + Resources + Calendar | **appointments + employee EXCLUDE** | `resource_id` مؤجل؛ منع التداخل على الموظف (D10) |
| المحاسبة | Journal Entries لكل مستند + Taxes + Payment Terms + Aging + Lock Dates | **journal_entries + fn_gl_post_entry + أرصدة شهرية + محرك فترات** | مطابق مفاهيمياً؛ عملة واحدة (D24) وميزان من الأرصدة الشهرية (أسرع) |
| الضريبة | `tax_calculation_rounding_method` (لكل بند افتراضياً) | **لكل بند + فرق إلى `rounding_difference`** (N5) | نفس افتراض Odoo، مع حساب صريح للفرق |
| الترحيل التلقائي | Automated Inventory Valuation + Anglosaxon COGS | **تسليم يُثبت التكلفة، فاتورة تُثبت الإيراد** (N4) | يفصل التكلفة عن الإيراد زمنياً — أثره ظاهر في تقارير المطابقة |
| المرتجعات | Credit Note + Return Picking | **مرتجع على الجدول الموحد + تكلفة الأصل snapshot** | مطابق (D22) |
| تعدد الشركات | `company_id` + multi-company في نفس القاعدة | **قاعدة منفصلة لكل عميل + Control DB** | عزل أقوى، وتكلفة تشغيل أعلى (D1 + 7A-0) |
| الشيكات | Full cheque lifecycle | **قبض/دفع فقط، والحالة الوسيطة حساب** | دورة الارتداد مؤجلة |

**الخلاصة:** نموذجنا **أكثر تقييداً** من Odoo في نقطتين (منع البيع المباشر، وإلزام الحجز) و**أبسط** في ثلاث (لا PO/RFQ، لا عملات، لا multi-company داخل القاعدة). هذا يقلّل الأخطاء التشغيلية ويزيد متطلبات الانضباط على المستخدم — ويجب أن ينعكس في تدريب المستخدمين (7H).

## 5) معايير القبول العامة (تُطبَّق على كل جزء)

| المعيار | القيمة | طريقة التحقق |
|---|---|---|
| التقارير الثقيلة | < 500ms على مليون بند | اختبار أداء موسوم `UBP_LOAD_ROWS` |
| إجراءات الشاشة | < 300ms (P95) | قياس في اختبار تكامل + Serilog |
| عدد الاستعلامات لكل شاشة | ≤ 3 (بدون N+1) | مراجعة كود + عدّاد Dapper |
| التزامن | تعارض الإصدار يُرجع 409 برسالة مفهومة | اختبار تزامن لكل مستند |
| الذرّية | فشل أي خطوة = لا أثر في DB | اختبار Transaction rollback |
| عدم قابلية التعديل | مستند مرحّل لا يُعدّل/يُحذف | اختبار Trigger مباشر |
| الصلاحيات | كل زر مسجّل + مفحوص على السيرفر | اختبار Registry |
| الترجمة | كل مفتاح في ar.json و en.json | اختبار تطابق المفاتيح |
| سقف الملف | كل ملف ≤ 300 سطر | فحص CI |

## 7) استراتيجية الاختبار وبوابة الإنجاز

| المستوى | التغطية | الأدوات |
|---|---|---|
| وحدة (Services) | قواعد الترحيل، الحسابات، السياسات | xUnit + PostgreSQL حقيقي (نمط `TestDb`) |
| تكامل (Repositories + SQL) | القيود، Triggers، FEFO، التزامن | xUnit + SQL مباشر |
| عقد الواجهة | كل شاشة 200 + كل زر مسجّل | نمط المرحلة 3 + فحص Registry |
| سيناريو (End-to-End) | حجز → تنفيذ → فاتورة → تحصيل → تسوية | اختبار واحد لكل دورة في كل جزء |
| أداء | 1M بند + 100 مستخدم | `UBP_LOAD_ROWS` + harness قرار 7F |
| تراجعي | اختبارات المراحل 1–3 (75) تمرّ بعد كل migration | CI إلزامي |

**Definition of Done لكل جزء:** migration + كود + شاشات + ترجمة + اختبارات + تحديث هذه الوثائق + نجاح كل الاختبارات القديمة.
